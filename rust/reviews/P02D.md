# P02D — reviewed zero-request GraphQL candidate

C031 needs to express a Rust candidate that rejects its input before credentials and makes no request, while frozen Deno makes one query. The R01H2 `graphql-fixture` delta could only shorten a script to a nonempty prefix, so the harness could not state that difference without hiding the fixture. P02D makes one narrow exception. A reviewed golden may request `candidate.graphql.steps: []` only when the frozen case has exactly one effect-free ordered group of exactly one query, with unchanged records and no asset or mutation step. The loader then derives a candidate-only fixture with `expectedRequests: 0` and `groups: []`. The golden format stays at v1, and the SHA pin, exact `approvedSurfaces` equality and required Rust User-Agent binding are unchanged. That binding cannot be observed when no request is made, so a zero-request candidate reports `userAgents: []`. Nonempty prefix and variable-replacement logic is unchanged. No dependency was added, no Rust command code changed, and no C031 case, golden or promotion is part of this item.

## Design

- `CaseSchema` and `GraphQLFixtureSchema` are unchanged. A frozen case still needs at least one group and one step per ordered group, and a direct zero-request frozen case fails `parseCase`. Only `CandidateGraphQLDeltaSchema` drops its `minLength(1)`.
- `ZeroRequestCandidateGraphQLSchema` is a strict object over the frozen fixture entries with `expectedRequests: literal(0)` and `groups: strictTuple([])`. It rejects nonempty groups, a nonzero count, an empty ordered group and extra fields.
- `applyGraphQLDelta` keeps every existing guard. After the effect-free/query guard and before the prefix map, an empty delta requires exactly one frozen step; otherwise it fails with `zero-request GraphQL delta needs exactly one frozen query step`.
- At load time, a zero delta validates the candidate's ordinary case fields with `parseCase({ ...candidateSpec, graphql: spec.graphql })`. It then parses the derived fixture with the zero schema and runs the normal `checkGraphQLFixture` and the candidate `resolveCase(..., graphqlUserAgent)` preflight. Nonzero deltas keep `parseCase(candidateSpec)`.
- After substitution, `resolveCase` uses the zero schema only when a User-Agent is passed **and** `groups` is an empty array. Baseline runs and the no-User-Agent dummy resolution stay on strict `GraphQLFixtureSchema`. `expectedRequests === 0` is deliberately not the gate.
- `run.ts`, `compare.ts`, `graphql-server.ts` and `lane-scheduler.ts` are unchanged. The candidate's localhost GraphQL server still starts. With no groups the scheduler is finished at creation, so any request reaching the listener, on any path, is counted as unexpected and fails `compareGraphQLFixture` on both the issue and the count. The lane's network denial covers other egress.
- `serve-case.ts` now exports its existing `resolveWithPort` so a test can drive the driver's own resolution. Its behavior is unchanged.

## Tests

`reviewed-golden.test.ts`:

- The existing two-query `[graphqlGolden([]), "Invalid"]` expectation is now the exact one-step rejection.
- **Zero delta loads.** On one-query `c016-default-team` the frozen spec is unchanged and still one step. The candidate view is the original fixture with `expectedRequests: 0, groups: []`. `resolveCase` with the User-Agent yields the zero fixture, and without it throws. The frozen spec still resolves to one request with and without the User-Agent.
- **Surfaces and preflight.** A zero delta combined with a changed stderr loads only with exactly `graphql-fixture`, `graphql-user-agent` and `stderr`. Candidate fields are still checked: an undeclared `{{cwd}}` placeholder fails the resolve preflight, and an over-cap close-after-bytes fails `parseCase`.
- **Zero delta rejections:**
  - a two-step baseline
  - a one-step mutation, or a mutation in a dropped suffix
  - an asset-only fixture
  - lanes
  - changed expected records
  - no GraphQL fixture
  - a missing Rust User-Agent
  - missing `graphql-fixture` or `graphql-user-agent` approval
  - an extra delta field
  - a forged golden SHA
- **Schema and resolution.** The zero schema accepts the exact shape and rejects nonempty groups, `expectedRequests: 1`, `[{mode:"ordered",steps:[]}]` and an extra field. `GraphQLFixtureSchema` and `parseCase` reject the zero shape. `resolveCase` rejects the zero shape without a User-Agent, and each malformed variant even with one.
- **`runCorpus` through Bubblewrap:**
  - The frozen baseline makes its one request with 2.6.0. The zero candidate passes with fixture `{requests: 0, unexpected: 0, authorizationMatched: [], userAgents: [], graphqlRequests: 0, assetRequests: 0}`, and counts as a reviewed-deviation pass but not a User-Agent-only pass.
  - A candidate posting the frozen request, or posting to `/elsewhere`, fails on the fixture surface; the `runCorpus` test pins both mismatch surfaces and the first detail. The `serve-case` test and confined reports pin the exact unexpected-request and count-mismatch details.
  - A baseline making no request is `baseline-drift` and the candidate never runs.
  - The loaded frozen spec is unchanged afterwards.

`serve-case.test.ts`: the zero candidate view resolves to zero requests only with its runtime User-Agent. The driver's server reports `expectedGraphQL` 0. No request compares clean, and a POST to `/graphql` or `/elsewhere` gives the exact unexpected-request and count mismatches.

This driver-level test exercises the empty scheduler, server and comparator together in place of separate unit tests for each component.

`f02b-v3-profile.test.ts`: every pinned profile entry expects at least one interaction. A zero-request fixture is rejected by `projectCase` for every pin (`target counts 0/0`), so the profile's own User-Agent resolution cannot admit one.

The new tests were checked against the implementation by temporarily mutating it and confirming each mutation turned a test red (all reverted before the final runs):

- `resolveCase` accepting zero without a User-Agent
- the zero branch allowing two frozen steps
- the zero branch deriving an empty ordered group
- dropping the load-time `parseCase`
- `compareGraphQLFixture` ignoring issues and counts

## Limits

- The zero exception covers only a frozen single effect-free query. A multi-request baseline, a mutation, an asset or lanes still need their own reviewed design.
- The required `graphql-user-agent` surface is unobservable for a zero-request candidate.
- Requests that bypass the loopback listener are covered by the lane's network denial, not by fixture comparison.
- The `resolveCase` zero-schema gate is internal: its current User-Agent callers receive a loaded, SHA-checked golden or a strict frozen spec. A future hand-built `CaseSpec` caller would need to preserve that reviewed-only invariant.
- C031E0 already froze `c031-bare-linear-url-legacy` and `c031-bare-linear-unsupported-legacy` with their bundle and digest guard. Their promotion and SHA-pinned Rust goldens, with `approvedSurfaces` derived from `changedSurfaces`, belong to the C031 Rust action.
