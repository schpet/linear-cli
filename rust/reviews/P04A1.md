# P04A1 review record: authenticated exact target exit status

P04A1 adds the native status helper and the authenticated `targetExit` observer to the confined Linux lane. It changes no C2 fixture, root app source, root lock, SDL, or candidate Rust code, and it leaves pipe topology and byte comparison untouched. P04A2 owns `closed-at-start` and `close-after-bytes(N)` stdout modes and their EPIPE proof; P04B owns PTY-delivered SIGINT. Neither this record nor the helper is a PTY, clock, process-stub, VCS, or Rust-candidate parity claim.

## Observer contract

`rust/parity/runner/helpers/status-helper.c` (C11) is the bwrap command for every confined invocation. The runner opens a fresh `127.0.0.1:0` listener and generates a random 128-bit nonce and opaque identity per run (`target-status.ts`). The helper receives `port nonce identity target argv...` in its own argv only, scrubs the nonce from its argv storage, connects with a `SOCK_CLOEXEC` socket **before** forking, sends one length-framed `HELLO`, and forks only after the runner's `ACK`. The child closes the socket explicitly and `execve`s the absolute target with inherited env, cwd and streams; a `CLOEXEC` pipe carries an exec `errno` back so an `execve` failure is a distinct helper exit 124 plus an `exec-failed` record, never a target `{code:127}`. The parent `waitpid`s the exact child (retrying `EINTR`), sends one bounded `RESULT` (`exited <code>`, `signaled <num> <NAME>`, or `exec-failed <errno>`), shuts down, and exits with the target code or `128+n`. Pre-fork exit codes 120–125 are documented in the source and in `HELPER_EXIT_CODES`; an unrecognized wait status or a signal outside the pinned 1–31 table fails the helper instead of reporting. The runner maps signal numbers through its own pinned Linux x86_64 table and rejects a name that disagrees with the number. The nonce is only a correlation token, not a secret: the helper argv scrub leaves it visible in bwrap PID 1's `/proc/1/cmdline`.

`runConfined` races `HELLO` against the outer exit so a `bwrap:` diagnostic or a helper setup exit is classified as soon as bwrap returns. It stores `outerExit` (engine view) and `targetExit` (authenticated) separately and requires `code==code` or `128+n==code`; an engine-observed SIGKILL never satisfies a target expectation. A second connection is refused (the listener closes on the first accept), and wrong nonce, wrong identity, wrong version, empty/oversize/non-ASCII/truncated frames, a RESULT before HELLO, EOF before RESULT, bytes after RESULT, a duplicate RESULT, a mismatched pid/name/number, and a late RESULT are all `TargetStatusError`, a harness failure that aborts the case and can never become baseline drift, not-implemented, or a proposed fixture. Only the runner's own timeout or output-cap kill leaves `targetExit` null; the timeout/truncated surfaces still report and the exit surface reports "no authenticated target status".

## Format addendum

`expected.exit` is now a strict union of exactly one `{code: integer 0..255}` or `{signal: "SIGTERM" | "SIGPIPE" | "SIGINT"}`; `{code,signal}`, empty objects, extra keys, unknown or lowercase names, numeric signals and `SIGKILL` are rejected. The P04 `expected.exit.signal` special rejection in `parseCase` is removed; `pty`, `terminal`, `clock`, `keyring` and `processes` remain rejected. Legacy `{code}` case bytes and meaning are unchanged (all 121 committed cases load and pass). `{"exit":{"code":143}}` and `{"exit":{"signal":"SIGTERM"}}` are distinct: the first is satisfied only by an authenticated `exited 143`, the second only by `signaled 15 SIGTERM`, although bwrap's outer status is 143 for both. `compareObservation` reads only `targetExit` for exit equality and still compares exact stdout, stderr and file effects. Reports carry `targetExit`, `outerExit`, the sandbox helper/target PIDs and helper provenance under `lane.statusHelper`. Proposal `exit` projects an authenticated signal to the strict loadable `{signal}` shape, omitting the observer-only `number`; unsupported signals fail proposal writing rather than producing an invalid case expectation. Proposal `outerExit` remains diagnostic.
