## Three-state input: hypothesis result and adapter

**`Option<Option<T>>` is rejected by the derive.** A temporary probe on `IssueUpdateInput` with `trashed: Option<Option<bool>>` and `skip_serializing_if = "Option::is_none"` failed `cargo check` with:

```
error: This field is not nullable but you're wrapping the type in Option.  Did you mean bool
  --> crates/linear-cli/src/graphql/operations/issue_update.rs:97:25
   |
97 |     pub trashed: Option<Option<bool>>,
   |                         ^^^^^^
```

The cause is in `cynic-codegen` `types/validation.rs`: `input_type_check` strips one `Option` for a nullable schema field and then reports `FieldIsRequired` for a second `Option`. The probe was removed before any other verification.

**Adopted mechanism: local `Edit<T>` adapter (`src/graphql/edit.rs`).** `Edit<T> = Unchanged | Clear | Set(T)` with a manual `Serialize` (`Clear` is `null`, `Set(v)` is `v`, `Unchanged` returns a Serde error instead of inventing a value) and `#[cynic(skip_serializing_if = "Edit::is_unchanged")]` on each nullable scalar field. Cynic's `InputObject` derive wraps a non-`Option` Rust type for a nullable schema field in `Option` (`types/alignment.rs`) and then asserts `Option<Edit<T>>: IsScalar<Option<Marker>>`, which Cynic's blanket impl reduces to `Edit<T>: IsScalar<Marker>`. `Edit<T>` forwards `cynic::schema::IsScalar` and `cynic::Enum` to `T`, so the schema check is retained rather than bypassed. `CoercesTo` was not needed: the input-object derive checks `IsScalar`/`Enum`/`InputObject`, not `CoercesTo` (that trait is used by the variables derive).

A second temporary probe confirmed the check still bites through the adapter. `title: Edit<bool>` on `title: String` failed with `` the trait bound `bool: IsScalar<String>` is not satisfied ... required for `Edit<bool>` to implement `IsScalar<String>` ... required for `Option<Edit<bool>>` to implement `IsScalar<Option<String>>` ``. `label_ids: Edit<Vec<String>>` on `labelIds: [String!]` failed with `` the trait bound `Vec<String>: IsScalar<String>` is not satisfied ... required for `Option<Vec<Edit<Vec<String>>>>` to implement `IsScalar<Option<Vec<String>>>` ``: the derive treats any non-`Option`/`Vec` wrapper as a single list item, so a list cannot sit inside `Edit`. Both probes were removed.

**Consequence for lists.** `labelIds`, `addedLabelIds` and `removedLabelIds` are `Option<Vec<String>>` with `skip_serializing_if = "Option::is_none"`: omitted or set (including `[]`). The oracle never sends `null` for a list field (`issue-update.ts` lines 413-470 only assign arrays), so no oracle state is lost; a future need for `list: null` requires a separate reviewed adapter. Nullable input-object fields (for example `TeamFilter.parent`) are not covered by `Edit` yet; a forwarding `cynic::InputObject` impl was deliberately not shipped without a derive that proves it.

`Edit<T>` is input-only. It carries a `Deserialize` impl only because `cynic::Enum` is declared as `Enum: DeserializeOwned + Serialize` (`cynic/src/core.rs`), so the forwarding `cynic::Enum` impl cannot compile without one; that impl now always fails with `Edit<T> is an input-only adapter and cannot be deserialized`. The earlier lenient impl (`null` to `Clear`, value to `Set`) would have made a missing field deserialize to `Clear`, because serde routes missing fields through `deserialize_option`; a wire test now proves `null`, a value, and a struct with the field missing all fail. The `Edit<Enum>` path is proven by the `slaType: Edit<SlaDayCountType>` field and its wire test. `Default` for `Edit<T>` is a manual impl with `#[allow(clippy::derivable_impls)]`, because the derive would add a `T: Default` bound that scalar newtypes such as `Json` do not and should not satisfy; `IssueUpdateInput` derives `Default` so callers name only the fields they edit.

## Variables, scalars, enums, union, output

- `GetTeamsVariables` omits `filter`, `first` and `after` when `None` (`#[cynic(skip_serializing_if = "Option::is_none")]`), producing exactly `{"first":100}` on page one and `{"first":100,"after":"cursor-a"}` afterwards, matching `team-list.ts`/`project-list.ts`. `first` is `Option<i32>` so the generated definition is `$first: Int` like the Deno document, not `Int!`; callers always pass `Some(100)`, and an unset `first` is omitted like any other `undefined` key (a test pins `{}`), never sent as `null`. Nested filter omission is proven with `TeamFilter { name: Some(StringComparator { eq: Some(..) }) }` serializing to `{"filter":{"name":{"eq":"Engineering"}},"first":100}`. The raw `api --paginate` path keeps `after: null`; the owned request envelope is shown to pass such a null through untouched (the raw transport itself is F02B/C083).
- Scalars are `String` newtypes for `DateTime`, `DateTimeOrDuration`, `Duration`, `TimelessDate`, `TimelessDateOrDuration`, `UUID` and `JSON`; `JSONObject` wraps `serde_json::Map`. Cynic's `Scalar` derive delegates Serde to the inner type, so numbers, arrays and objects are rejected where a string is expected and strings/arrays/numbers where an object is expected. `JSON` text is not parsed or validated; it is kept verbatim.
- Enums use `rename_all = "lowercase"` (`AgentActivityType`) or `"camelCase"` (`AgentSessionStatus`, `AgentSessionType`, `SLADayCountType`), so `thought`/`awaitingInput`/`onlyBusinessDays` round-trip exactly and `THOUGHT`, `Thought`, `AWAITING_INPUT` fail with `unknown variant`. Cynic's `Enum` derive owns both Serde impls and emits the schema spelling on output.
- `AgentActivityContent` variants are named after the union members because Cynic matches inline-fragment variants by variant name (a first attempt with short names failed with `Could not find a member named Prompt in the union`). The `Unsupported(String)` fallback receives `__typename`; `ensure_supported()` returns a typed `UnsupportedActivityContent` naming it, and the manual `Serialize` refuses the fallback so it cannot reach `--json` output. Cynic adds `__typename` to the union selection; the Deno document does not select it. This is a request-level difference for the future `issue agent-session view` parity review, not something F02A can remove, and the response `--json` shape never emits it.
- Response structs derive a separate `serde::Serialize` with `rename_all = "camelCase"` or explicit `rename = "type"`, fields declared in document order, no `skip_serializing_if`, no `flatten`, no `default`. A golden test asserts `serde_json::to_string_pretty` of a two-team connection byte for byte, including `description: null`, `archivedAt: null` and `endCursor: null`, and a second golden covers the full agent session with `type`, nulls and both union members. `serde_json`'s `preserve_order` was enabled after the first test run showed a `JSONObject` fixture re-sorted (`content` before `type`); with it, embedded objects and raw `Value` payloads keep server order, which the oracle's `JSON.stringify` also preserves.

## Envelope and error classification (types only; no HTTP)

`GraphQlRequest<V>` (`query`, optional `variables`, optional `operationName`) is owned here and built from `cynic::Operation` by `with_variables` or `without_variables`; absent keys are omitted, matching the oracle's dropped `undefined` values.

`parse_response::<T>` reads the envelope with `data: Option<serde_json::Value>` and `errors: Option<Vec<GraphQlError<Value>>>`, classifies in this order, and decodes `data` into `T` only on the success path:

1. Body is not parseable JSON (`serde_json` category `Syntax`/`Eof`; `Io` is grouped with them so the match stays exhaustive): `MalformedJson`, `AppErrorKind::Transport`, message `response body is not valid JSON: ...`.
2. Body is JSON but not an envelope (non-object top level, `errors` not an array, an error without `message`): `UnexpectedShape` (category `Data`).
3. `errors` is non-empty: `GraphQl { errors, partial_data }`, whatever `data` holds. `partial_data` is true for any non-null `data`, including `{"issueUpdate":null}` or `{"agentSession":null}`, which the previous typed-first decode would have misreported as a shape failure because those root fields are non-null in `T`.
4. `data` absent or `null` with no errors: `MissingData`.
5. `data` present but not decodable as `T` (wrong scalar type, missing non-null field, null non-null root field without an error, unknown enum variant): `UnexpectedShape`, `AppErrorKind::Invariant`, message `response JSON did not match the expected operation shape: <serde detail>`, with the `serde_json::Error` retained as `source()`. `Invariant` is used because the types were compiled against the committed schema, so a valid JSON body contradicting them is a broken contract rather than a transport or GraphQL failure; F02B may re-map it when it owns the full error surface.

`require_success` and `require_entity` give `MutationRejected` and `MissingPayloadEntity` without command wording. GraphQL errors are `cynic::GraphQlError<serde_json::Value>`, keeping `path`, `locations` and `extensions`; `graphql_message` prefers a non-empty `extensions.userPresentableMessage` and falls back to `message`, and `is_not_found` reproduces the oracle's substring rule. `GraphQl`, `MissingData`, `MutationRejected` and `MissingPayloadEntity` map to `AppErrorKind::GraphQl`. HTTP status, rate limiting, IO and cancellation are F02B.

## Known differences for F02B compatibility

The fresh independent Claude closeout of the corrected 19-file diff returned **ship**. It reproduced all 44 GraphQL tests and cached Clippy/fmt/generator checks, verified both null-root GraphQL-error regressions, schema checks and absence of unsafe/casts/secret logging. The full closeout feedback is in the coordinator's untracked notebook (`F02/claude-f02a-closeout-feedback.md`). Nonblocking observations: a malformed error item without `message` is an `UnexpectedShape` here; terminal escape sanitization of a presentable message belongs to the eventual renderer.

- **`{"data":null}` with no `errors` is an error here, not in Deno.** graphql-request 7.4.0 (`build/legacy/helpers/runRequest.js`) returns `data: executionResult.data` for any 2xx body without errors, including `null`; the Deno command then fails later with a TypeError when it reads a field of `null`, which `handleError` renders as a generic failure. The Rust envelope reports `MissingData` (`response contained neither data nor errors`, `GraphQl` kind) at the boundary instead. A Linear server should never produce this body for the three non-null root fields, so no oracle capture is expected to exercise it; F02B should keep the stricter behavior and note it in the parity harness rather than reproduce the TypeError.
- **Well-formed JSON that contradicts the types is `UnexpectedShape` (`Invariant` kind).** Deno has no equivalent boundary; it would surface as a later TypeError or as wrong output. F02B decides the final `AppErrorKind` mapping and exit text when it owns the transport error surface.
- **`errors` classification matches graphql-request 7.4.0's `isExecutionResultHaveErrors`**: an empty `errors` array is not an error; any non-empty array is, regardless of `data`. Non-2xx bodies (which graphql-request wraps in `ClientError` whether or not they parse) are F02B.
