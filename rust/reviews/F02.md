## Transport design as built

- `EndpointUrl::parse` requires `http`/`https`, a host, no credentials, no fragment; keeps path and query for requests; `Display`/`Debug` show only `scheme://host[:port]`. `ApiKey::new` rejects empty and any byte outside `0x20..=0x7E` (so CR/LF, tab, ESC, DEL, non-ASCII), allows spaces, stores a `HeaderValue` marked sensitive, and redacts itself. `Deadline` (non-zero, default 30 s) and `ResponseCap` (non-zero, default 8 MiB, ceiling 64 MiB, no unbounded mode) are validated newtypes. `ProxyMode::{Direct, HttpsConnect{url, bypass_loopback}}` and `CaMode::{PublicRoots, PublicRootsPlusPem(PathBuf)}` are the typed config; `ProxyUrl::parse` requires `http`, a loopback host, no credentials/path/query/fragment.
- `GraphQlTransport::new` builds one `reqwest::Client`: `http1_only()`, `redirect(Policy::none())`, `referer(false)`, `timeout(deadline)`, `retry(reqwest::retry::never())`, then `no_proxy()` for `Direct` or `proxy(Proxy::https(url).no_proxy(NoProxy::from_string("127.0.0.1,localhost")))` for `HttpsConnect`, then `add_root_certificate` for every certificate from `Certificate::from_pem_bundle` on the CA file. All of these compile with exactly `default-features = false, features = ["rustls-tls-webpki-roots"]`; the proxy API is available without `system-proxy`. The CA file must be a regular file (`symlink_metadata`), non-blank, a valid PEM bundle with at least one certificate; because `from_pem_bundle` only checks PEM framing, each certificate is also loaded into a throwaway root store at construction so a bad DER is reported as `CaPem` for that path rather than as a generic client-build error. Nothing falls back to public roots on a bad file.
- Headers are set per request, not as client defaults: `Authorization: <key>`, `User-Agent: schpet-linear-cli/2.6.0` (`concat!` of `CARGO_PKG_VERSION`, pinned by a test), `Content-Type: application/json`. The wire test proves each appears exactly once and no `Referer` is sent.
- `send_raw(document, Option<Map>, Option<&str>)` and `send_request(&GraphQlRequest<V>)` return `RawHttpResponse { status, headers, body: Vec<u8> }` for every status without parsing; `RawHttpResponse::Debug` prints counts, not header values or bytes. `execute::<T, V>` calls the same path and then `classify_typed`, which is also public so a raw response can be classified later.
- Body collection: if `Content-Length` already exceeds the cap the body is not read; otherwise `Response::chunk()` is called repeatedly with checked addition and stops before exceeding the cap. Both paths give `ResponseTooLarge { status, limit }`; a body exactly at the cap is returned intact. The whole exchange (connect, send, body) runs under `tokio::time::timeout(deadline)`; reqwest's own client timeout is set to the same value and its `is_timeout()` maps to the same `Timeout` variant.
- Classification (`classify_typed`, reusing F02A's `parse_response` unchanged): (1) any body whose envelope carries non-empty `errors` is `GraphQl { status, headers, errors, partial_data }` regardless of status, so 400 validation errors and 401 auth errors keep their status but present as GraphQL errors; (2) non-2xx without GraphQL errors is `Http { response: Box<RawHttpResponse>, body }` (boxed so `Result<T, TransportFailure>` stays under Clippy's `result_large_err` threshold) where `body` is `Data` (a valid envelope under a 5xx) or `Unusable(ResponseError)` (malformed JSON, wrong shape, missing data), always retaining the raw response; 3xx lands here because redirects are never followed; (3) 2xx with a bad body is `Response(ResponseError)`, i.e. F02A's `MalformedJson`, `UnexpectedShape` or `MissingData`. `success:false` and a null payload entity are typed successes at the transport level; `require_success`/`require_entity` keep F02A's `MutationRejected`/`MissingPayloadEntity`.
- Network failures: `Timeout { origin, deadline }` and `Network { origin, phase: Connect|Request|Body|Other, source }`. Every `reqwest::Error` enters the module only through `SanitizedReqwestError::new`, which calls `without_url()`; `Display` appends the innermost source message (for example `Connection refused (os error 111)`). `AppError` mapping: `GraphQl` → `GraphQl`; `Http`, `ResponseTooLarge`, `Timeout`, `Network` → `Transport`; `Response(e)` → F02A's mapping (`MalformedJson` → `Transport`, `UnexpectedShape` → `Invariant`, `MissingData` → `GraphQl`); `RequestBody` → `Invariant`. TLS and proxy failures are not yet distinguished from other `Network` failures: classifying them from the source chain needs a controlled TLS/proxy failure, which is Gate 2.
- `paginate(fetch)` calls `fetch(None)` first (built-ins omit `after`) and `fetch(Some(cursor))` afterwards, accumulates typed nodes, returns the last `PageInfo`, and fails on `hasNextPage` without a non-empty cursor (`MissingCursor`), on a cursor equal to the one just sent or seen before (`RepeatedCursor`), or on any page fetch error (`Fetch { page, source }`), discarding earlier pages. No page limit. `pagination::PageInfo` has `From<teams::PageInfo>` so F02A's operation types are untouched.

## Deno fixture driver (`serve-case.ts`)

Runs as `deno run --frozen --cached-only --no-prompt --config rust/parity/deno.json --allow-read=<root>/rust/parity,<root>/graphql/schema.graphql --allow-net=127.0.0.1 --allow-env=NODE_ENV serve-case.ts <case>`; `--allow-env=NODE_ENV` is required because the npm `graphql` package reads it at load time. Argument rules, all checked before any stdout line and exiting 2: exactly one argument; non-empty; no `..` segment; resolved parent must equal `runner/transport-cases`; kebab-case `.json` name; the directory and the file must not be symlinks and the file must be a regular file. The case is loaded with `loadCases(transportCases, manifestRoutes, id)` (so every file in the directory is validated), must have `graphql != null`, and is resolved per port through `resolveCase` with the existing `fixturePort` substitution. It imports P03B's `startGraphQLServer`, `loadPinnedGraphQLSchema` and `compareGraphQLFixture` unchanged. Protocol: one `{"event":"ready","port","path","expectedRequests","expectedGraphQL"}` line (reading `expectedGraphQL` first rejects lanes/assets before readiness); stdin EOF is completion and any stdin byte is a protocol error (exit 2); one `{"event":"final","requests","consumed","expected","unexpected","issues","mismatches"}` line; exit 0 only with no mismatch; `stop()` in `finally`. The Rust side (`FixtureDriver` in the test) spawns with piped stdio and `kill_on_drop`, reads the ready line under a 30 s deadline, closes stdin, reads the final line and reaps under a 30 s deadline, asserts nothing follows the final line, and kills/reaps on any failure. `Deno.serve`'s `shutdown()` returned promptly with an idle keep-alive connection from the Rust client still open (measured with a Python `http.client` probe and in every driver-backed test).

## Tests

`tests/graphql/` now has 79 tests (44 F02A + 7 pagination + 28 transport, including the closeout Debug-redaction test); `contracts` (13) and the binary/library unit tests (2 + 2) are unchanged. Deno: `serve-case.test.ts` has 7 tests after the two closeout `writeAllSync` tests.

Serial isolation of the Deno-driven tests: each one is a plain `#[test]` whose body runs through `run_serial`, which takes the process-wide `std::sync::Mutex` on the test thread, builds a current-thread Tokio runtime inside the guard, runs the async body, and drops the runtime (and any `kill_on_drop` child) before the guard is released. The first version held the guard inside `#[tokio::test]` bodies, which Clippy 1.93 rejects as `await_holding_lock` (12 errors in `clippy2.log`); the refactor keeps exactly one fixture child alive at a time without an async-aware mutex. The raw-socket tests stay `#[tokio::test(flavor = "current_thread")]` and run in parallel because each binds port 0 and owns no shared state; the ambient-proxy control re-executes the test binary once and its inner run does not need the lock.

Pagination (`tests/graphql/pagination.rs`, scripted pages, no network): first page asked with `None` and later pages with the previous cursor; single page keeps its `pageInfo`; `hasNextPage` with `null` or `""` cursor is `MissingCursor` with no further fetch; a cursor equal to the one just sent is `RepeatedCursor` on page 2; a cursor seen earlier (`a`, `b`, `a`) is `RepeatedCursor` on page 3; a page-2 fetch error is `Fetch { page: 2 }` with `source()` set and no nodes returned; error messages name the page.

Transport value types: `EndpointUrl` keeps path/query, displays only the origin, rejects `ftp`, credentials, fragment, non-URLs; `ApiKey` allows spaces and rejects CR/LF injection, tab, ESC, non-ASCII and DEL at the exact byte index, redacts `Debug`/`Display`; `Deadline`/`ResponseCap` reject zero and a cap above 64 MiB; `ProxyUrl` accepts `127.0.0.1`, `localhost`, `[::1]` and rejects `https`, non-loopback hosts, credentials, path, query, fragment; `HttpsConnect` with and without loopback bypass builds a client; CA modes reject a missing file, a directory, a whitespace-only file, non-PEM text and a PEM block with bogus DER (`CaRead`/`CaNotRegularFile`/`CaEmpty`/`CaPem`), so no invalid bundle can fall back to public roots.

Local raw-socket server (`LocalServer`, `std::net` on a thread, stops via channel):

- exact wire: `POST /graphql HTTP/1.1`, exactly one `authorization: lin_api_fake`, `user-agent: schpet-linear-cli/2.6.0`, `content-type: application/json`, no `Referer`, body bytes `{"query":"...","variables":{"after":null},"operationName":"Q"}` (a raw `after: null` passes through untouched);
- secret sanitization: endpoint `http://127.0.0.1:<closed>/graphql?signature=SIGNED-SECRET-TOKEN` with key `lin_api_SECRET_KEY_VALUE` gives `Network { phase: Connect }`; `Display`, `Debug` and the full `source()` chain (reqwest error plus its io source, at least two links) contain neither the token, `signature`, the key, nor `/graphql`; the transport's own `Debug` does not contain the key; the `AppError` is `Transport` with a source;
- **direct-mode ambient-proxy control**: the test re-executes itself with `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY` and their lowercase forms all set to `http://127.0.0.1:1` (nothing listens) and `NO_PROXY` removed; the `Direct` transport still reaches the loopback server and gets its 200. Mechanism (verified in the vendored sources, corrected after the Gate 1 review): disabling `system-proxy` does **not** stop reqwest from reading those variables. `ClientBuilder::build` (`reqwest-0.12.28/src/async_impl/client.rs:419`) pushes `ProxyMatcher::system()` whenever `auto_sys_proxy` is still true, and that matcher is hyper-util's `Matcher::from_system` (`hyper-util-0.1.20/src/client/proxy/matcher.rs:238`), which always starts from `from_env` (`ALL_PROXY`, `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` and lowercase forms); the `system-proxy` feature (`hyper-util/client-proxy-system`) only adds the macOS/Windows platform lookups on top. What excludes the ambient variables is that `ClientBuilder::proxy` and `ClientBuilder::no_proxy` both set `auto_sys_proxy = false` (`client.rs:1414-1430`), and `GraphQlTransport::new` always calls exactly one of them (`no_proxy()` for `Direct`, `proxy(..)` for `HttpsConnect`). The throwaway root-store clients in `load_pem_bundle` call neither, so they do consult the ambient variables at construction, but they send no request. The control proves the outcome; the mechanism is the builder flag, not the feature. A positive "the proxy would have broken it" control is not possible for a plain-HTTP loopback endpoint, because `Proxy::https` only intercepts `https` URLs; that is Gate 2's TLS lane;
- response cap: a `Content-Length: 4096` body under a 1024-byte cap is `ResponseTooLarge` without reading; a 1024-byte body under a 1024-byte cap is returned intact (and `RawHttpResponse::Debug` prints `<3 headers>`/`<1024 bytes>`); an endless chunked body under a 2048-byte cap stops in well under the 5 s deadline;
- deadlines: a server that reads the request and never answers, and one that sends headers plus a body prefix and stalls, both give `Timeout` at a 300 ms deadline (measured ≥ 250 ms and < 3 s), with `Transport` kind and message `request to http://127.0.0.1:<port> did not complete within 300ms`; no partial body is returned;
- cancellation: a 30 s-deadline request to the stalling server dropped by an outer 150 ms `tokio::time::timeout` returns in under 2 s; after dropping the transport, the server thread observes the client's close **while the current-thread runtime is still running** (`released while the runtime was running: true`), under a 2 s hard deadline, before the runtime is dropped. Nothing about synchronous teardown is claimed beyond that observation.
